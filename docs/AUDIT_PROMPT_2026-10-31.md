# スパイス＆ハーブ検定 学習アプリ 徹底監査プロンプト（Claude Code 用）

以下は監査の実行指示です。この文書をそのまま Claude Code への指示として使います。

---

## 0. 役割と最優先原則

あなたは、この学習アプリの独立品質監査責任者です。開発者とは独立の立場で、証拠に基づいて検証してください。

優先順位は次のとおりです。

1. **原本忠実性**（教科書の範囲・内容と一致しているか）
2. **機能正確性・データ整合**
3. **UI/UX（ユーザーの実際の使い方に合っているか）**
4. **要件充足**
5. セキュリティ・保守性

厳守事項：

- 証拠のない指摘をしないこと。指摘には必ずファイルパス・行番号・再現手順・根拠を付けること。
- 判定は PASS / FAIL / PARTIAL / BLOCKED / NOT TESTED / NOT APPLICABLE を区別し、**未検証の項目を PASS としない**こと。
- 事実・推測・解釈を区別すること。数値・件数を創作しないこと。網羅率は分母・分子・範囲を分けて示すこと。
- 一次情報を優先すること（原本画像、公式資料、実データの再集計）。要約や過去の報告書の記述を鵜呑みにせず、自分で再集計・再実行して確認すること。
- 重要な結論は、可能なら別の方法でも検証すること（例：アプリの表示値と、原データを独立スクリプトで数えた値の突き合わせ）。
- この監査は**読み取りとローカル実行が基本**です。コードやデータは変更しないでください。修正が必要な点は「指摘＋修正案」として報告すること。GitHub への push、PR 作成、コミットは行わないでください。

- ローカルでの主な確認コマンド（package.json の scripts を正とすること）:
  - `npm run typecheck` / `npm run test`（Vitest）/ `npm run validate:data` / `npm run build` / `npm run test:e2e`（Playwright、本番ビルド＋vite preview に対して実行）
- CI: `.github/workflows/ci.yml`（check ジョブ＝型・単体・データ検証・ビルド・npm audit、e2e ジョブ＝Playwright）。

## 3. ユーザー指示の反映確認（受入基準）

以下はユーザーが実機で使って出した指示です。**全件**について、現在のコードと実際の挙動の両方で、指示どおりになっているかを確認してください（コードに存在するだけでは不十分で、E2E または実挙動で確認すること）。

### 学習導線・ホーム
- UX1: ホームに「とりあえず5問」など、設定なしで始められる導線がある。
- UX9: 「とりあえず5問」では絞り込みと学習フォーカスを表示しない（設定 UI を出さずにすぐ解ける）。

### 暗記モード（/memorize）
- UX10: 答え合わせをしなくても次に進めるボタンがある。
- UX10: 説明からスパイス＆ハーブ名を当てる逆モードがある（自己評価は同じカードの復習記録に反映される）。
- UX10 微調整: 逆モードの切替ボタンは画面の下の方にある。「次へ（答え合わせしない）」ではなく「次へ」という短いラベルである。

### 単語帳（/cards）
- UX10: 自己評価（分かった／あいまい／分からない）と「次のカード」が、カードの真下にあり、スクロールなしで届く。表面でも「裏面を表示」でめくれる。
- UX13: 種別・章・並びのプルダウンと「シャッフルし直す」は、カードやボタンの下（画面下部）にある。

### 画面遷移・レイアウト共通
- UX11: 黄色い説明ブロック（badge）は各画面の末尾（下部）にある（ホーム、改訂ポイント画面で確認）。
- UX11: 電子書籍を開いた後に他のタブへ移ると、スクロール位置が最上部に戻る（電子書籍画面自体の読書位置は守られる）。
- UX12: スクロールなしで気楽に遊べるよう、全体の余白（特に上部の隙間）が詰まっている。**上部バー（ヘッダー／ナビ）の太さ・寸法は変わっていない**こと（ユーザー指示 2026-10-30「上部バーの太さは変えないこと」）。
- UX12: 回答後、模範解答は「正解／不正解」のすぐ下に出る。解説・出典などの詳細は、開くまで隠れている（スクロールで初めて出る位置関係でよい）。
- UX8: 上部バーの並びは ホーム／演習／苦手／間違い／ブックマーク／暗記／単語帳／模擬試験／改訂／電子書籍／検索／設定 の12件。

### 演習（/practice）・検索（/search）
- UX13: 演習の設定（モード・出題順・問題数）と「絞り込みと学習フォーカス」は、問題の下にある。検索の「絞り込み条件」は検索結果の下にある（キーワード入力は上）。
- 対象外として意図的に上に残しているもの: 設定画面（設定自体が目的）、問題内のプルダウン（対応付け・自己採点＝解答入力そのもの）。この線引きが妥当かも評価すること。

### 改訂ポイント（/revision）と電子書籍（/reader）
- 「4訂版 p.N を読む」ボタンを押すと、**その節の先頭ではなく、指定したページそのものへ着地する**こと。特に、複数品目を含む長い節（例: その他の品目 p.98〜108）で、p.102（しそ／ジュニパーベリー）、p.103（セロリー）、p.105（パンダンリーフ）、p.106（レモンバーム）の各ボタンが、それぞれ正しいページに着地することを実挙動で確認すること。
- 改訂データのページ番号・変更内容が、財団の公式資料（2026年3月）と 4訂版（2026年版）の実ページに一致すること（例: タイム p.71、唐辛子 p.76、ナツメッグ p.78、パセリ p.80、ジュニパーベリー p.102、セロリー p.103、カリカットの地名変更の方向）。
- リーダー内の索引からのページジャンプも、指定ページに着地すること。

## 4. 監査観点

### A. 原本忠実性・データ整合
- 第2節の基準値を全て独立に再集計する（転記ページ集合・文字数、知識単位数と照合状態、問題数・形式数・難易度分布、カード数、模試プール数、原画の実在と復号可否）。
- 転記テキストと原画の照合: 全数照合が現実的でない場合は、抽出方法（無作為＋重点ページ）を明示したうえで照合する。重点ページ: p.8（カリカット）、p.71（タイム）、p.76（唐辛子）、p.78（ナツメッグ）、p.80（パセリ）、p.91（ローレル）、p.92（わさび）、p.102〜106（その他の品目）、p.139〜147（予想問題・本物の索引）。
- 節の開始ページ表（structure.ts の bookPage）が、各節の転記レコードの実ページ範囲と整合するか全81節で機械検証する（±1 ページの境界共有は許容として扱い、それ以外は指摘する）。
- 改訂ポイントの全項目について、ページが「そのページの転記を含む節」へ解決されることを機械検証する。
- 問題の正答検証: 形式ごとに抽出して、正答が出典（転記テキスト）と一致するか確認する。記述式は rubric と modelAnswer の整合を見る。

### B. 問題・採点エンジン
- 採点の境界ケース（部分点、複数選択、対応付け、並べ替え、記述式のキーワード採点）を通読とテストで確認する。
- 模擬試験の出題規則（対象プール、形式の除外、級別の構成）が仕様どおりか。
- SRS（間隔反復）の計算、学習記録の保存・復元、ストアの移行（旧データの読み込みで壊れないか）。

### C. アプリ機能・UI/UX
- 全12画面の表示・遷移・状態（読み込み中、空状態、エラー境界）。
- 検索（節・問題の横断検索、絞り込み、件数表示の正確さ）。
- PWA（Service Worker の更新挙動、古いビルドが残り続けないか）、ダークモード、フォントサイズ設定。
- アクセシビリティの基本（ボタンのラベル、タップ領域 44px 以上、キーボード操作）。

### D. テスト・CI
- ローカルで全テストスイートを実行する（型・単体・E2E・データ検証・ビルド）。結果は件数まで正確に記録する（末尾だけの確認で済ませない）。
- **既知の問題: 2026-10-31 の CI（main `6b976d7c`、run 41151735522）で check ジョブは成功したが e2e ジョブが失敗した。失敗したテストの内訳は未特定である。ローカルで再現し、失敗テストを特定して原因を報告すること。**
- テストの質も監査対象とする（アサーションが実装の文言に引きずられていないか、位置・配置のテストが実際のユーザー体験を表しているか、フレーク要因はないか）。

### E. 公開サイトとの整合
- 公開サイト https://sylpica.github.io/spice-herb-master/ が、どのコミットのビルドを表示しているか（index.html のアセットハッシュで判定）。
- **既知の状態: gh-pages は現在も UX10 世代のビルドのままで、main の最新（UX11〜UX13＋ページジャンプ修正）は未反映である。この世代差を監査結果として明記すること**（コードの監査と公開状態の監査を混同しない）。

### F. セキュリティ・依存関係
- `npm audit` の結果（CI では実施済みのはずだが、ローカルでも可能な範囲で確認）。
- 秘密情報・個人情報がリポジトリに含まれていないか（スキャン原画や設定ファイルを含む）。
- 依存のライセンスと極端に古い依存の有無（概要レベルでよい）。

## 6. 判定と報告の形式

### 指摘の重大度

- P0: 学習内容の誤り、採点の誤り、データ損失など、利用に直接害があるもの
- P1: 主要機能の不具合、指示未反映
- P2: 限定的な不具合、表示・導線の問題
- P3: 軽微な改善点、将来のリスク

### 報告書

監査結果は `docs/AUDIT_REPORT_BY_CLAUDE_CODE.md` に書き、最終報告メッセージも同じ内容で出すこと。構成は次のとおり。

1. 監査の範囲と方法（何を、どうやって確認したか。再集計・照合・実行したコマンドと結果の件数）
2. 基準値の再集計結果（第2節の各値について、実測値と一致／不一致）
3. ユーザー指示の反映確認（第3節の全項目に PASS/FAIL/PARTIAL/NOT TESTED の判定と証拠）
4. 指摘事項一覧（重大度順。各件にファイル・行番号・再現手順・根拠・修正案）
5. CI の E2E 失敗について（再現したか、失敗テスト名、原因の切り分け結果）
6. 公開サイトの状態（表示されているビルドの世代と、main との差）
7. 未検証・BLOCKED の項目（理由と、何があれば検証できるか）
8. 最終判定（次の4領域ごとに、合格／条件付き合格／不合格／未検証 のいずれかと、その根拠を1〜2行で）
   - 教材（原本忠実性・データ整合）
   - 問題・採点
   - アプリ（機能・状態管理）
   - UI・UX（ユーザー指示の反映を含む）
9. 修正の優先順位の提案（やるべき順番と理由。実施はしない）

### 報告の作法

- 最終報告は日本語で、結論を先に書くこと。
- 「問題なし」と書く場合は、何を確認した結果そう言えるのかをセットで書くこと（確認していないことは「問題なし」に含めない）。
- 前任者（Muse）の過去の監査報告書（`docs/MUSE_AUDIT_REPORT.md`、`docs/AUDIT_REPORT_2026-10-30-2.md`、`docs/AUDIT_REPORT_2026-10-30-3.md`、`docs/AUDIT_REPORT_2026-10-31-4.md`）は参考資料として読んでよいが、その結論を検証なしに引き継がないこと。特に第4回報告書で PARTIAL とされた3件（単語帳・演習・検索の配置テストの集計取り直し、改訂ボタンの着地 E2E）は、今回の監査で決着させること。
- 判断記録は `docs/DECISIONS.md`（#1〜#51）にある。仕様の意図が不明な場合はまずここを参照すること。
